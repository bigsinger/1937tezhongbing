# 十二关任务恢复说明

## 结论

十二个正式关卡 `m000`—`m011` 的任务骨架不是只能在事后凭感觉重新编排。当前已经恢复并数据化：

- 关卡标题、任务简报图索引和主要目标；
- 目标之间的先后依赖；
- 救援、击毙、拾取、爆破、占点和撤离等条件类型；
- 多目标计数与按 scene 去重；
- 限时、角色损失和特殊失败条件；
- 关卡中的任务标记、爆破检测、出口、出生点和入口坐标；
- 全部必需目标完成后的胜利判定。

这些内容已经整理在 `game/data/missions.json`，由通用 `MissionState` 计算进度，并通过 `MissionRuntime` 与实际关卡实体连接。当前主场景已能从战斗和交互产生救援、角色击毙、物品拾取、爆破/占点、区域清敌、撤离、限时和必要角色损失事件。任务目标完成、失败和胜利会立即回写到界面。

这表示任务已经具备“世界动作 → 规范化事件 → 目标依赖/计数 → 胜负”的可玩工程闭环，不再只是静态任务清单。原程序 `sub_404BB0` 的逐关指针初始化和 `sub_405410` 的十二路胜负分支均已重新审计；老赵、铁蛋、强子、古明、大牛五个全局角色指针也已由运行时 type 2/9/1/10（或伪装后的 91）/8 交叉定案。m001/m002/m003/m004/m005/m006/m008 不能由通用任务图表达的原生类型、距离边界和物品持有人条件，已经固化为独立的源码证据规则，详见 [原版关卡专用交互与任务求值恢复](ORIGINAL_MISSION_INTERACTIONS.md)。十二关第一版对白节奏、scene-binding 镜头提示、教程门控、AI 配合和连续难度曲线现已独立整理在 `mission_direction.json`，由通用导演/AI 协调器执行；其中无法由原资源证明的内容均标为 `remake_editorial`，详情见 `MISSION_DIRECTION.md`。逐关完整通关录像与实机数值校准仍是后续持续工作。

## 恢复证据链

### 1. VWF/SLIST 关卡事实

十二个正式 VWF 均可解析到精确文件末尾，共有 19,199 条实体记录。每条实体可关联到 DBL 对象名称、类别、世界坐标、参考坐标和可选巡逻数据。

任务相关 DBL 项已确认：

| DBL ID | 原显示名 | 规范化类型 | 用途 |
|---:|---|---|---|
| 1001 | 藏尸处 | `corpse_state` | 尸体/发现状态锚点 |
| 1008 | 检测视线精灵 | `sight_detector` | 视线或剧情检测 |
| 1010 | 进入表示 | `entrance` | 进入点 |
| 1011 | 日军出兵处 | `enemy_spawn` | 敌人出生点 |
| 1018 | 标注 | `marker` | 编辑器中的可见任务标记 |
| 1019 | 检测爆炸精灵 | `explosion_detector` | 爆破目标检测 |
| 1020 | 检测出口精灵 | `exit_detector` | 撤离/占点检测 |

其中 24 个爆破检测和 12 个出口检测都能在 32 像素内唯一配对到一个任务标记。另有 7 个独立任务标记，用于军服箱、剧情 NPC 等叙事位置。位置和配对关系可以机械生成并验证。

### 2. 任务控制流

VWF/SLIST 本身保存场景事实，不保存一份完整的高层任务图。已审计 SAV 也按其结构精确结束，没有附加任务脚本；`M1937.SI0` 中可识别的 IBLOCK 是 320×240 存档缩略图。

目标依赖、计数、限时和胜负分支来自原程序中十二关任务控制流的恢复。简报文本和任务图用于给控制流中的实体指针、计数器和分支赋予可读语义。恢复结果再与 VWF 中实际存在的 scene 和锚点数量交叉验证。

### 3. 新运行时数据模型

规范化任务定义不复制旧引擎代码，而是使用事件条件：

```json
{
  "id": "destroy_airfield",
  "depends_on": [],
  "condition": {
    "event": "trigger_activated",
    "where": {"display_name": "检测爆炸精灵"},
    "required_count": 6,
    "unique_by": "scene_index"
  }
}
```

`MissionState` 对事件名称和 payload 做通用匹配，因此同一个状态机可以处理十二关，而不需要为每关复制一套胜负代码。新增的 `MissionRuntime` 位于世界系统和状态机之间，负责：

- 在关卡开始时确认每个 `scene_bindings` 都存在于当前 `level.json`，并核对爆破/出口等绑定的锚点类型；
- 拒绝缺少 scene 引用、跨关卡或未绑定 scene 的救援、拾取、击毙、剧情锚点、爆破和撤离事件；
- 把救援、拾取、角色击毙、剧情锚点和区域清敌等事实按稳定身份去重；
- 暂存依赖尚未满足的持久事实，在前置目标完成后重新回放，避免“先拾物、后完成击毙”造成永久卡关；
- 保持撤离区域为瞬时判定，不把一次短暂进入错误缓存为永久事实；
- 只允许 `advance_time()` 产生限时失败，防止世界系统伪造 `time_expired`。

当前世界事件入口为：

| 世界行为 | 规范化事件 |
|---|---|
| 靠近并按 `E` 解救任务 NPC | `entity_rescued` |
| 击毙与任务角色绑定的实体 | `role_eliminated` |
| 按 `E` 拾取场景物品或角色掉落 | `item_acquired` |
| 在没有原生求值规则的兼容目标上按 `E` 激活持久任务锚点 | `trigger_activated` |
| m001/m002/m004 的 type 98 被真实 `128×64` 世界爆炸摧毁 | `trigger_activated` |
| m003/m008 的 type 98 严格 128 像素内生成 type 85 定时炸药 | `trigger_activated` |
| m008 修复规则下按 `F` 手动引爆矿坑炸药 | `explosion`（仅 `repaired` 规则要求；默认稳定 MOD 判定不包含该步骤） |
| 到达剧情锚点 | `story_anchor_reached` |
| 清除当前关卡全部 faction 1 敌人（m009 修复后必需目标） | `area_hostiles_cleared` |
| m010 四名指定队员分别同时进入四个制高点 | `simultaneous_zones_occupied` |
| 存活队员与已救 NPC 到达出口 | `trigger_activated` / `party_at_trigger` |
| 必要队员或护送 NPC 死亡 | `required_character_lost` |
| 计时达到关卡上限 | `time_expired` |

第一关 `m000` 的两个救援对象（scene 1427、1428）和出口（scene 1600）已按关卡实体绑定：营救两人后，存活队员和获救人员都进入 128 像素出口范围才完成撤离；必要角色死亡会失败。这是当前最明确的端到端任务闭环，也是其余关卡复用事件协议的基线。

### 4. 原生爆破求值与兼容策略

原程序求值器现已直接证明五个稳定 MOD 分支的目标语义，不能再用“走到标记旁按 `E`”代替：

- m001/m002/m004 要求对应 type 98 的生命值降至非正；Remake 只在真实 `128×64` 爆炸椭圆覆盖目标时推进；
- m003/m008 要求每个 type 98 的严格 128 像素范围内存在 type 85；物品 45 在 type 10 攻击命中帧生成 actor 85 时消费一次，任务层只观察世界状态，不会二次扣除；
- m001/m004 的地图物资本来就不足以为每个目标部署物品 45，可由手榴弹、油桶或其他真实世界爆炸完成，不再使用“预置炸药 + E”的早期便捷近似。

`charge_policy` 仍保留为没有专用原生求值器的兼容数据策略。真实 DBL/VWF 可以证明每关 DBL 998 炸药拾取物和爆破 scene 数量，但不能单独证明所有分支的消耗调用；因此该策略的来源状态仍为 `remake_policy_from_recovered_map_inventory`：

| 关卡 | DBL 998 / 爆破目标 | 模式 | 交互语义 |
|---|---:|---|---|
| m001 | 1 / 2 | 原生 type 98 判定 | 不直接按锚点；真实爆炸使目标生命归零 |
| m002 | 1 / 1 | 原生 type 98 判定 | 物品 45 依照世界动作消费；真实爆炸使目标生命归零 |
| m003 | 6 / 5 | 原生 type 85 判定 | 每处严格 128 范围内放置一份定时炸药 |
| m004 | 0 / 2 | 原生 type 98 判定 | 使用真实世界爆炸/火源，不强造背包炸药 |
| m008 | 4 / 4 | 原生 type 85 判定 | 每处严格 128 范围内放置一份定时炸药 |
| m009 | 9 / 4 | `inventory_required` | 四个列车目标各消耗 1 份 |
| m011 | 4 / 6 | `preplanted` | 按简报修复为六目标后不强行制造两份炸药，不扣背包 |

`MissionData` 仍会拒绝未知兼容模式、目标数量与 scene 绑定不一致，以及 `inventory_required` 但地图炸药少于所需数量的任务。对原生分支，库存消费属于 type 10 世界动作，任务事件只在 actor 85 出现或 type 98 被真实爆炸摧毁后发布；失败、重复交互以及对目标按 `E` 都不会消费物品或推进任务。m009/m011 等尚未接入专用原生爆破求值器的内容继续服从其数据化 `charge_policy`，不会反向覆盖上述五关。

### 5. 任务事件媒体提示

任务可以可选声明 `media_cues`，把 `audio`、`dialogue`、`movie` 或 `ending` 绑定到四类已验证时机：

| 段 | 键 | 触发条件 |
|---|---|---|
| `on_start` | 单个 cue | 非 headless 简报关闭后 |
| `on_objective` | objective ID | 该目标首次完成时 |
| `on_story_anchor` | role ID | 剧情锚点事件真正完成新目标时 |
| `on_victory` | 单个 cue | 任务进入胜利状态时 |

每个 cue 必须把 `source_status` 标为 `recovered_media_mapping`、`remake_editorial` 或 `mixed`；未知标签、引用不存在的目标/锚点，或缺少相应媒体字段都会让任务目录校验失败。当前实际接线只有：

- m000：关闭简报后显示明确标为 `remake_editorial` 的教程提示；首次完成 `rescue_pengxin` 后播放强子 `acknowledge`，其触发编排同样标为重制编辑；强子是 m000 原 VWF 中唯一可控队员（scene 1436），早期误用老赵语音的接线已经修正；
- m006：只有选择 `repaired` 规则时，scene 1461 的接头锚点首次完成 `follow_contact` 才显示 `remake_editorial` 提示对白；默认稳定规则没有该补写目标，重复事实也不会重播模态对白；
- m011：胜利时按 `recovered_media_mapping` 打开与原资源映射一致的结局图，并在资源缺失时显示“十二关任务全部完成”。

这证明任务事件与媒体导演之间已经有数据驱动接口，也避免把编辑提示伪装成原剧情；它不表示十二关对白、镜头或过场已经恢复完成。

## 关键关卡的最终控制流语义

### m004：计划书携带者

原任务 case 5 检查物品 101；关卡 VWF 的 `auxiliary[0]` 携带物记录显示 scene 2637 持有该物品，同名候选 scene 2548 不持有。因此 `m004_plan_officer = [2637]` 已从候选升级为最终绑定。击毙 scene 2637 后生成带 `original_item_id = 101` 的计划书掉落。其他角色可以实际拾起并携带它，但只有物品当前位于古明或大牛的 `+0x228` 背包容器时才满足原 case 5；运行时周期检查实际容器，错误持有人不会推进，之后仍可通过丢弃和转交纠正，旧存档也不依赖一次性拾取标签。

### m006：物品 101 必须由强子取得

原 case 7 初始化只保存 type 15 孙大麻子、type 22（DBL“王老板”，剧情身份为加藤）和 type 100 出口。实际胜利分支只检查：

1. type 15 与 type 22 均已死亡；
2. 强子的背包容器存在；
3. 强子持有物品 101。

原始物品清单同时证明 scene 1457 孙大麻子确实携带物品 101。进一步离线恢复的 `sub_459840` 表明：他在 scene 1462/type 100 检测对象 32 像素内时，先以五次动态 actor 工厂取数在自身 `x-16` 处创建 actor 101/GFL 246 文件袋，再从背包移除物品 101。`sub_4596E0` 则让 scene 1460/type 22 加藤在 256 像素内直接追踪该文件袋；抵达后沿 `sub_456AB0` 把物品转入自己的背包，并以四次析构取数删除 actor 101。该链路不依赖通用诱饵接受表、朝向或视线。

Remake 已恢复这条动态交接、地面文件袋原 SPR、存档中途恢复和“加藤死亡后只掉落一份名单”的所有权闭环。若孙大麻子在交接前死亡，名单从他的真实容器掉落；若已交给加藤，则不会再从旧角色绑定凭空复制第二份。默认 `stable_mod` 仍只允许由强子的实际拾取完成名单目标；scene 1461 接头点与 scene 1462 出口不参与原始胜利。`repaired` 才保留此前按叙事补写的“尾随—接头—双刺杀—撤离”流程和对应编辑对白。`legacy_m006_exchange_test.gd` 以真实 m006 资源直接验证 32/256 边界、5/4 次随机事务、存读档、转交和唯一掉落，不执行人工通关。

### m008：原始判定没有额外手动引爆

原 case 9 检查四个 type 98 目标附近是否均存在 type 85 放置物，然后检查老赵、大牛是否都在 type 100 出口 128 像素内。控制流中没有“完成布置后再按一次 F 才能胜利”的条件，也没有“提前按 F 立即任务失败”的分支。因此：

1. `stable_mod`：四处布置完成后，老赵和大牛进入 scene 802 即可结束；
2. `repaired`：保留手动引爆演出和提前引爆失败，作为明确的可选现代修复规则。

### m009：全关清敌是修复后的设计意图

原 case 10 会扫描全关仍存活的 faction 1 单位，而不是检查一个可恢复的“车站几何边界”；但该扫描结果因控制流缺陷没有参与最终判断。原版实际必要路径只保留四个列车爆破目标和老赵存活。复刻提供两套显式规则：

1. `stable_mod`（默认）：老赵存活并激活 scene 1714—1717 四个列车爆破目标；
2. `repaired`：再要求从 scene 1610、1611 取得两份物品 101 交接文件，并把全关 faction 1 日军清零。

“全关清零”不是尚未找到车站边界时的临时近似，而是 `repaired` 对原控制流未使用结果的明确修复决定。两套 profile 都保存在 `missions.json`，设置与存档分别持久化 `mission_rule_mode`；稳定模式不会运行描述修复目标的补写导演节点。

### m010：四人同时占点

原 evaluator 对四个出口检测 scene 1620—1623 做连续实时检查。每个区域使用包含边界的 128 世界像素半径，并要求该区域附近至少有老赵、强子、大牛、古明之一；铁蛋不能替代。原代码没有额外记录“不同区域必须使用不同角色”的身份约束，真实地图上的四个区域彼此相距很远，因此同一次评估自然需要四人分处四地。复刻忠实使用这个逐区域存在性条件，不累计先前占领，不要求停留时间，也不要求先清敌。主场景当前每 0.2 秒自动检查，因此不再通过靠近后按 `E` 逐点激活。任务仍受 3,600 秒时限和这四名角色的存活约束。

## 已识别的数据差异

恢复过程保留了不一致信息，避免用一个看似整齐的名称掩盖证据：

- `m005`：原始 GFL 简报 1053 的叙事名“阿贵”与 scene 736 / DBL 908 的资源显示名“阿全”已经定案为同一 runtime type 24 角色的别名；稳定角色 ID 为 `m005_agui`，其真实物品 101 只能由老赵、强子或古明持有后完成任务；
- `m004`：计划书军官已确认是 scene 2637；scene 2548 的同名资源不携带原任务检查的物品 101，不再列为待定候选；
- `m006`：剧情中的加藤孝一由旧引擎 type 22 / DBL“王老板”资源承担；scene 1457 孙大麻子携带的物品 101 已恢复为强子必须取得的真实名单掉落；
- `m008`：手动引爆和提前引爆失败不在实际 case 9 胜利控制流中，只属于显式 `repaired` 规则；
- `m009`：原控制流确有全关 faction 1 存活扫描，但结果因缺陷未被使用；默认 `stable_mod` 忠实复现实际生效路径，`repaired` 才要求两份文件、全关清敌和四个列车爆破；
- `m011`：原版存在爆破目标指针覆盖缺陷；默认 `stable_mod` 观察 scene 1353 后还要求老赵、强子抵达 scene 1359，`repaired` 按简报要求六处目标，见下一节。

这些项目属于需要人工判读和运行校验的“语义层”，但不会阻止场景坐标、锚点计数和任务状态骨架自动化。

## m011 原版指针覆盖缺陷

第十二关有六个爆破检测实体：scene 1348、1349、1350、1351、1352、1353。任务简报也要求炸毁军机、指挥塔和油库等共六处目标。

原版初始化逻辑把六个目标指针连续写入同一个存储位置，也把出口指针按扫描顺序覆盖。前五个 type 98 赋值都被下一次覆盖，最终只剩 scene 1353；唯一 type 100 则最终为 scene 1359。随后胜利检查先要求最后 type 98 失效，再要求存活的老赵和强子都进入最后 type 100 的 128 像素范围。这是原版实现缺陷，不是关卡中缺少五个锚点。

`repaired` 任务数据的修复意图是：

```text
required_count        = 6
unique_by             = scene_index
intended scene binding = 1348..1353
```

也就是要求六个不同爆破目标，和简报及关卡布置一致。默认 `stable_mod` 则只接受 scene 1353 作为爆破目标，随后仍要求老赵、强子进入 scene 1359，忠实复现稳定 MOD 的实际指针结果。`MissionRuntime` 会把两种模式的事件都限制在当前关卡 `scene_bindings`；`unique_by = scene_index` 防止同一目标重复计数。自动门禁会证明前五个 scene 不能在稳定模式误触胜利、1353 单独完成后仍不能胜利、两名角色到达出口才闭环，同时再跑一遍修复模式的“指挥官 + 六目标 + 西北撤离”世界动作闭环。

## 哪些内容可以自动化

在格式和语义映射已经确认之后，下列工作可以由工具生成或严格校验：

- 十二关地图尺寸、19,199 个实体和全部坐标；
- DBL 资源/显示名/类别关联；
- 巡逻当前航点索引、缓存航点世界坐标与 waypoint；其中持久标志 `+0x0C` 的启停语义尚未得到运行时代码证明；
- 七类任务锚点的 scene、坐标和类型，以及标记/爆破/出口/出生/入口五类锚点的逐关数量清单；
- 36 个爆破/出口检测与标记的一对一近邻配对；
- 十二关任务 JSON 的 schema、目标 ID、依赖、计数、去重字段和限时；
- 运行时目标进度、失败和胜利判定。
- 任务 scene 白名单、锚点类型、事件去重、依赖回放和瞬时出口语义校验。

这使后续关卡实现以“连接事件”为主，而不是重新猜测每个爆破点和出口在哪里。

## 哪些内容仍需人工校准

静态数据和控制流不能完整给出以下体验层信息：

- 对白文本出现时机、人物语气和字幕停留时间；
- 镜头移动、过场站位、动作衔接和音效同步；
- 尚未从对应原分支恢复的任务检测区域、阶段性特定角色和多人条件；m001/m002/m003/m008 的 128 边界、m004/m005/m006 物品持有人和 m010 四区条件已不属于该缺口；
- 敌人 AI 配合、增援时机、警戒反应和难度数值；
- m008 的 `F` 手动引爆和“布置四处前引爆失败”仅保留在 `repaired` 规则；默认稳定规则不把补写演出伪装成原版条件。胜负求值已经闭合，仍待校准的是爆炸视觉、声音和镜头演出；
- m006 等仍有旧引擎资源名与剧情名差异的最终呈现；m005 已使用稳定角色 ID 显式表达叙事名/资源名别名；
- 原版缺陷是修正还是提供兼容模式的产品决策。

因此最合理的流程是：先由恢复数据生成任务骨架和自动测试，再逐关试玩、录制和校准演出，而不是先手工搭十二套脚本再反向猜测原作。
