# 原版 VWF 关卡制作与验证方法论

## 1. 适用范围与结论

本文适用于在《1937特种兵》原版二进制引擎上，通过 VWF、运行时重定向和
兼容层制作扩展关卡。它不描述已停止扩张的 Godot 复刻工程。

项目当前支持两种关卡制作模式：

| 模式 | 做法 | 适用情况 | 新鲜度 | 风险 |
|---|---|---|---:|---:|
| `redeploy` | 保留一张完整原地图，重新部署角色、目标和巡逻 | 任务闭环优先、快速制作 | 中 | 低 |
| `composite` | 重新组合空间区域，再部署任务和敌军 | 需要明显不同的地图布局 | 高 | 中 |

`m012`、`m013` 属于 `redeploy`；`m014` 属于 `composite`。后者复用的是
原版房屋、院墙、道路和植被等美术积木，不复用一张完整旧地图。

必须区分四个不同层次：

1. **能解析**：文件签名、长度和结构合法；
2. **能加载**：原引擎进入关卡且进程保持响应；
3. **能完成**：真实任务状态机可按预期推进至成功，也能正确失败；
4. **好玩且可发布**：路线、难度、视觉、性能和故事均通过验收。

前三者中的任何一个都不能单独代替第四个。

## 2. 不可破坏的设计原则

### 2.1 已知版本优先

- 每个源 VWF 必须登记 SHA-256；
- 运行补丁仅支持 SDK 中已经验证的 `M1937.exe`；
- 哈希不符时停止生成，不通过“猜偏移”继续；
- 新发现字段先命名为 `unknown_*`，证据充分后再升级语义名称。

### 2.2 地图与任务状态机分离

VWF 保存地形、对象、位置、巡逻和占用，但没有一份可自由替换的完整任务
脚本。任务顺序仍由 `M1937.exe` 内的 12 套原版状态机决定。

制作扩展关前必须先选择一套语义相符的任务骨架，例如：

- 第 12 关：指挥官、六个破坏目标、撤离；
- 第 7 关：接头、两个目标、撤离。

不得只因为 scene 数量相近就套用状态机。故事目标、scene 身份、触发顺序、
失败条件和撤离条件必须能够一一对应。

### 2.3 一次变换必须覆盖完整数据闭环

移动地形区域时，下列内容必须作为一个事务同步处理：

- L1 地表；
- L2 视线/射击遮挡；
- L3 移动障碍和动态占用；
- L4 事件层；
- L5 人工通行修正；
- scene 世界坐标与参考坐标；
- 巡逻工作数组、正式路线数组和缓存坐标；
- 重新部署对象原位置与新位置的动态占用。

只移动背景图片或只改人物坐标都会产生穿墙、幽灵阻挡、路线偏移或任务
触发错位。

### 2.4 生成物不可手工漂移

`Mod/1937mNNN.vwf`、合成地形图和验证报告都应由设计源重新生成。正式
修改应落在：

- `mission-package.json`；
- `mission.json`；
- `blueprint.json`（仅 `composite`）；
- 生成器源码。

不得直接在最终 VWF 上做无法复现的十六进制修改。

## 3. 标准关卡包结构

```text
MapEditor/Missions/mNNN/
├── mission-package.json  # 构建、路由和确定性哈希清单
├── mission.json          # 故事、scene、部署、巡逻和质量阈值
├── blueprint.json        # composite 模式才需要
├── Build-Mission.ps1     # 关卡专用便捷入口
├── composition.md        # composite 自动生成
├── validation.md         # 自动生成
└── README.md             # 本关设计说明
```

模板位于 `MapEditor/Missions/_template`。`mission-package.json` 是统一入口的
契约，至少固定：

- 关卡 ID、选择器编号和复用的引擎任务号；
- 源/输出 VWF 的仓库相对路径；
- 运行时等长文件名；
- 制作模式；
- 设计源与报告路径；
- 已审阅输出的确定性 SHA-256。

其机器结构由 `MapEditor/Missions/mission-package.schema.json` 固定；
`composite` 模式缺少蓝图、合成报告或预览字段时，清单不完整。

所有相对路径都由构建脚本限制在仓库根目录内，避免错误写到项目外。

## 4. 从构想到发布的九道质量门

### G0：题材与任务骨架

先完成一页设计简报：

- 年代、地点和历史背景；
- 玩家角色及初始装备假设；
- 主目标、可选目标、失败条件和撤离方式；
- 对应原版任务状态机；
- 目标 scene 与状态机检查点的映射；
- 预期时长、潜行/战斗比例和难度曲线。

退出条件：故事与状态机可以逐项映射，没有“文档说完成但引擎不会判定”的
目标。

### G1：源数据与结构

- 校验 `M1937.exe` 和源 VWF 哈希；
- 解析世界头、五层网格和 `SLIST1`；
- 记录尺寸、scene 总数、活动对象、任务锚点和巡逻点数量；
- 确认所有将要编辑的 scene 真实存在；
- 确认巡逻点数量不会因等长修改而变化。

退出条件：未知版本、越界 scene、损坏记录或错误源文件均被硬拒绝。

### G2：空间蓝图

`redeploy` 模式：

- 明确哪些区域保留、哪些活动对象重新部署；
- 避免出生点继续落在原关卡高压战区；
- 路线必须利用新部署形成不同节奏，而不是只换目标名称。

`composite` 模式：

- 区块尺寸必须整除地图；
- 来源区块映射必须是无重复全排列；
- 正式“全新合成图”要求所有区块离开原位置；
- 尽量沿道路、空地、河岸或围墙自然断点切块；
- 避免建筑、门、桥、院墙和大型 sprite 跨切线；
- 先检查区块边缘 L2/L3 是否能合理衔接，再接受排列。

当前 `VwfBlueprintComposer` 支持同一张 VWF 内的平移重排，不支持旋转、
镜像、缩放、跨关卡混合或手绘新增 tile。文档中应称其为“区域重组新布局”，
不能夸大为完全从零绘制。

退出条件：结构等价、区块排列合法，并输出地表指纹、同位变化率和 scene
位移率。建议合成图同位地表变化率不低于 60%；低于该值应解释新鲜度来源。

### G3：任务与敌军部署

`mission.json` 至少声明：

- 全部玩家 scene；
- 全部参与出生安全检查的敌方 scene；
- 玩家出生格；
- 真实任务 scene 必达列表；
- 所有重部署对象的格坐标、朝向和巡逻；
- 出生安全距离；
- 最低全图连通率；
- 原版引擎允许的单段巡逻 A* 步数上限。

当前默认建议：

- `minimum_reachable_walkable_ratio >= 0.95`；
- 敌军初始位置距出生点至少 800 世界单位；
- 敌军巡逻点距出生点至少 600—800 世界单位；
- 大地图建议 `maximum_patrol_segment_path_length <= 64`；更低预算优先；
- 更高 AI/听觉配置下，再按实际发现时间人工加大安全区。

距离只是第一层门槛。仍需检查敌军朝向、视线遮挡、远程攻击距离和警报
传播，防止“距离够远但出生即被看见”。

### G4：静态导航与占用

`VwfMissionBuilder` 必须通过：

- 源哈希和输出结构等价；
- 编辑对象原占用清除、新占用建立；
- 玩家到每个真实任务 scene 的八方向 A*；
- 每一段保留或改写巡逻路线的 A*；
- 每一段巡逻 A* 不超过关卡声明的运行时预算；
- 对角移动不穿越障碍夹角；
- 从出生点可达通行格比例达到清单阈值；
- 初始敌人及巡逻点满足安全距离。

A* 通过只证明几何可达，不证明门的开闭时机、移动单位堵路、任务阶段锁定
或战斗后仍能通过。

还要区分“可达”和“能由旧引擎持续计算”。原版引擎在单线程主循环中为
活动对象更新路径；少量横跨大地图的巡逻段就可能让一张静态检查完全通过的
地图长期占满一个逻辑核。应同时记录每段步数的最大值、P95 和参与长路线的
活动对象数。需要表现大范围警戒时，优先拆成多个局部巡逻区，通过警报传播
和阶段事件实现联动，不要让单个敌人用一条路线遍历全图。

### G5：视觉与语义预览

使用 MapEditor 打开最终 VWF，至少检查：

- 地形预览与五层数据属于同一布局；
- 区块接缝没有断路、半栋建筑、悬空门或墙体错接；
- 人物、房屋、庄稼和前景的绘制层级合理；
- 出生点、目标、出口和巡逻轨迹没有落在墙内；
- 选中每个关键活物，完整路线与方向符合设计；
- 小地图上的目标分布和玩家行进节奏合理。

截图只截游戏/编辑器窗口，压缩后保存；文字优先用本地 OCR，不上传原图。
视觉检查结论应写入关卡 README 或评审记录，而不是只留在聊天中。

### G6：原版引擎运行探针

通过 `OriginalLevelProbe` 验证：

- 选择器关卡号映射到预期引擎任务；
- VWF 文件名在本进程内重定向正确；
- 原 EXE 和存档未被改写；
- 菜单、任务简报和地图阶段持续响应；
- 最终逻辑/渲染画布符合稳定配置；
- 大地图四个合法相机边界均能访问，覆盖范围与 VWF 世界尺寸一致；
- 探针不移动物理鼠标、不截取完整桌面。

建议至少运行 40 秒。该门只能证明载入与初始阶段，不等于通关。

### G7：完整玩法验收

每关至少保留：

- 一条从开始到胜利的完整记录；
- 每个主要失败条件的一次记录；
- 保存后读取并继续完成的一次记录；
- 不同难度下的敌军发现、警报和弹药消耗数据；
- 关键门、狭路、巡逻交叉点和撤离点的阻塞检查。

推荐遥测：

- 首次接敌时间；
- 警报次数和最大同时追击数；
- 各阶段耗时；
- 受伤/死亡与读档点；
- 弹药和补给剩余；
- P95/P99 帧时间、最长卡顿和关卡加载时间。

只有 G7 通过后，才能把“可加载关卡”升级为“可发布关卡”。

### G8：发行回归

- 选择器显示关卡名称并检查 VWF 存在；
- `dinput.dll` 对应关卡号、引擎任务和文件名重定向一致；
- `Patch` 源码与 `Mod` 编译产物同步；
- 更新故事、使用说明、截图和关卡数量审计；
- MapEditor 发布版能够打开新关；
- Git LFS 正确管理 VWF 和完整地形图；
- 本机存档、配置和运行生成文件不得提交；
- 本地构建、SDK 校验及 GitHub Actions 全部通过。

## 5. 统一构建方式

从仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File .\MapEditor\tools\Build-MissionPackage.ps1 `
  -MissionId m014
```

默认候选文件写入系统临时目录；开发者也可以用 `-WorkDirectory` 指定自己的
工作区。也可以运行关卡目录内的 `Build-Mission.ps1`。

统一构建器按 `mission-package.json` 自动完成：

1. 限制并解析仓库相对路径；
2. 校验清单版本、关卡 ID、选择器编号和引擎任务号；
3. `composite` 模式先生成合成 VWF 和预览图；
4. 部署 scene、巡逻和占用；
5. 执行结构、出生、连通和逐段 A* 检查；
6. 重新读取输出；
7. 将 SHA-256 与已经审阅的确定性基线比较。

首次新关应让零值基线主动失败。候选 VWF 和报告只保留在工作目录，不覆盖
已发布文件。审阅候选、预览和实机结果后，再登记实际哈希；以后同一设计源
若生成不同哈希，构建必须失败并要求人工解释。

## 6. 修改后的回归矩阵

| 修改内容 | 最低必跑检查 |
|---|---|
| 故事/文档 | scene 与任务语义人工复核 |
| `mission.json` | G3、G4、G5、G6、G7 |
| `blueprint.json` | G2—G7，重新生成预览 |
| VWF 解析/写入代码 | 三个扩展关全部重建、哈希与结构测试 |
| 选择器或代理 | 1、12、13、14、15 关运行探针 |
| SDK 地址/结构 | SDK 离线校验、代理 x86 构建、对应运行探针 |
| 渲染/输入配置 | 菜单和地图内鼠标、F1、M、底栏、窗口/全屏回归 |

## 7. 版本与证据管理

- `mission-package.json`、`mission.json`、`blueprint.json` 是设计源；
- `composition.md`、`validation.md`、运行探针报告是证据；
- `Mod/1937mNNN.vwf` 是可玩生成物；
- 每次接受新的输出哈希，提交说明必须写明原因；
- 运行截图采用压缩图，原始帧不进入仓库；
- 原版地址和结构统一进入 `SDK/`，不得在新工具里复制另一套裸地址；
- 推测、编辑补写和原版恢复内容必须在文档中明确区分。

## 8. 当前仍不能自动证明的内容

现有工具尚不能自动保证：

- 区块接缝视觉自然、跨边界大型 sprite 完整；
- 门、桥和可破坏物在所有生命周期下持续可通；
- 敌人视线、听觉、攻击和警报组合不会造成出生秒杀；
- 所有任务阶段、失败条件、保存读取和撤离能完整闭环；
- 关卡难度、补给量和通关时间具有良好平衡；
- 原版状态机之外的全新目标类型。

这些不是“以后再看”的模糊事项，而是 G5/G7 的强制人工与实机门。后续
MapEditor 应逐步把接缝、对象 footprint、视线/听觉热区和任务图校验变成
可视化、可自动失败的质量检查。

## 9. 发布完成定义

一个扩展关只有同时满足下列条件才算完成：

- 设计源可从干净仓库一条命令生成；
- 输出哈希确定；
- 五层、scene、巡逻与占用同步；
- 出生安全、全图连通和全部必达路径通过；
- 原引擎正确加载并持续响应；
- 完整胜利、主要失败、存读档均已实测；
- 视觉接缝、图层和路线通过编辑器评审；
- 选择器、补丁、文档、截图、发布版和 CI 同步。

缺少任何一项时，应在关卡 README 中明确标为“实验关”或“待完整通关验收”，
不能用“结构检查通过”替代产品完成度。
